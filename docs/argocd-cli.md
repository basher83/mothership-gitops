# ArgoCD CLI

The `argocd` CLI is a system tool installed and upgraded through Homebrew, not
pinned in this repo's `mise.toml`. This guide covers how it reaches the
`talos-prod-01` ArgoCD instance, the failure modes seen in practice, and the
commands used for routine inspection and the manual sync gates.

## Two Access Modes

The CLI keeps its contexts in `~/.config/argocd/config`, and `argocd context`
shows which one is active. Two contexts exist for this cluster, and they reach
ArgoCD by different paths.

| Context | Mode | Path to ArgoCD |
|---------|------|----------------|
| `kubernetes` | Core (`core: true`) | Kubernetes API through kubeconfig; no ArgoCD session |
| `argocd.tailfb3ea.ts.net` | Server (`grpc-web: true`) | ArgoCD API server through the Tailscale Ingress |

Core mode bypasses the ArgoCD API server and its RBAC entirely. It acts with
whatever Kubernetes identity the kubeconfig context carries, which for the
operator contexts is cluster-admin. Server mode authenticates to ArgoCD itself
and is subject to ArgoCD accounts and `policy.csv`.

## Core Mode

Core mode reads ArgoCD's ConfigMaps and Application resources from the
namespace set on the active kubeconfig context. Neither `talos-prod-01`
context sets a namespace, so core-mode commands fail with:

```text
configmap "argocd-cm" not found
```

The fix is a dedicated kubeconfig context that reuses an existing cluster and
user entry but sets `namespace: argocd`. Do not add the namespace to
`talos-prod-operator.tailfb3ea.ts.net` itself: that context is generated by
`tailscale configure kubeconfig` (see
[ADR-002](adrs/ADR-002-enable-tailscale-api-server-proxy.md)), and
regenerating it would drop the setting. A namespace on the shared context
would also change the default for every `kubectl` command.

```bash
SRC=talos-prod-operator.tailfb3ea.ts.net
kubectl config set-context talos-prod-argocd \
  --cluster="$(kubectl config view -o jsonpath="{.contexts[?(@.name==\"$SRC\")].context.cluster}")" \
  --user="$(kubectl config view -o jsonpath="{.contexts[?(@.name==\"$SRC\")].context.user}")" \
  --namespace=argocd
```

Then point core-mode commands at it explicitly:

```bash
argocd --core --kube-context talos-prod-argocd app list
```

`SRC` can be either kubeconfig context. Both were verified on 2026-11-07:
`talos-prod-operator.tailfb3ea.ts.net` (Tailscale API server proxy) and
`omni-talos-prod-01` (Omni proxy). The Omni user authenticates through the
`kubectl oidc-login` exec plugin, so without a cached token the first call
waits on a browser OAuth flow before the command runs.

## Server Mode

Server mode talks to `argocd-ha-helm-server` through the `argocd` Tailscale
Ingress (`apps/argocd-ingress/ingress.yaml`). The server runs with
`server.insecure: true` and TLS terminates at the Tailscale proxy, so the CLI
must use gRPC-web. The saved context already has `grpc-web: true`; pass
`--grpc-web` on a fresh login.

No SSO is configured. Authentication uses the local `admin` account. The admin
password has never been rotated: `admin.passwordMtime` in `argocd-secret`
matches the creation time of `argocd-initial-admin-secret`, which still exists
and holds the live password. Read it with `argocd admin initial-password -n
argocd` or from that Secret. Never commit or paste the value.

```bash
argocd login argocd.tailfb3ea.ts.net --grpc-web --username admin
argocd context argocd.tailfb3ea.ts.net
```

Sessions expire. An `Unauthenticated ... Token is expired` error means the
saved context still exists but needs `argocd relogin`.

The `radar` local account is API-key only with `applications, get`. It exists
for Radar's Git-rendered diffs and is not an operator login; see
[`../specs/radar-in-cluster.md`](../specs/radar-in-cluster.md).

## Common Commands

The examples below use server mode. In core mode, prefix each with
`--core --kube-context talos-prod-argocd`.

```bash
argocd app list
argocd app get <app>
argocd app diff <app>
argocd app sync <app>
```

`argocd app get` and `argocd app diff` are read-only and safe at any time.
Before running `argocd app sync`, check the sync policy exceptions in
[`architecture.md`](architecture.md). Never pass `--prune` to `longhorn`,
`longhorn-helm`, or `coredns-tailscale`.

The manual gates (`argocd-ha`, `argocd-ha-helm`, `anthropic-oauth-proxy`) are
promoted with `argocd app sync`. Run `argocd app diff` first and read the
result, because these gates exist precisely so a human reviews the change.
`argocd-ha` creates `argocd-ha-helm` but does not sync it, so promoting
ArgoCD HA takes two syncs:

```bash
argocd app diff argocd-ha
argocd app sync argocd-ha
argocd app diff argocd-ha-helm
argocd app sync argocd-ha-helm
```

## Version Skew

Homebrew tracks the latest `argocd` release, while the server version follows
the chart behind the manual `argocd-ha-helm` gate. The two can drift apart by a
major version. `argocd version` reports both when a server session is
available. Skew matters most in core mode, where the client reads server-side
ConfigMaps and CRDs directly.

As of 2026-11-07 the Homebrew client is v3.6.1 and the live server is v2.14.11
(chart `7.9.1`). Git pins `argo-cd` chart `10.*`, so the next `argocd-ha-helm`
promotion is a major ArgoCD v2 → v3 upgrade, not a routine sync. Review the
upstream upgrade notes before running it.
