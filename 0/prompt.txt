 The audit is explicitly scoped:

 │ “longhorn has root-app prune: false”

 The architecture document is not:

 │ “longhorn | prune: false | Pruning storage resources risks data deletion”

 — docs/architecture.md:40-44.

 That table distinguishes argocd-ha from nested argocd-ha-helm, but does not similarly mention longhorn-helm. Calling this “carefully

 Where the Resources Actually Live

 Live Argo inventory shows that longhorn-helm owns:

 ```console
   CustomResourceDefinition  23
   DaemonSet                   1
   Deployment                  2
   ConfigMap                   3
   Service                     4
 ```

 Those CRDs include:

 ```console
   backups.longhorn.io
   replicas.longhorn.io
   snapshots.longhorn.io
   volumes.longhorn.io
 ```

 None currently carries Argo or Helm prune protection:

 ```console
   CRD                    argocd sync-options  helm resource-policy
   backups.longhorn.io    -                    -
   replicas.longhorn.io   -                    -
   snapshots.longhorn.io  -                    -
   volumes.longhorn.io    -                    -
 ```

 This makes the child policy materially relevant. Argo CD documents pruning as deletion of resources no longer defined in the desired
 source. Kubernetes documents that deleting a CRD “removes all custom objects that were stored under that definition”; recreating it
 starts empty (Kubernetes CRD documentation
 (https://github.com/kubernetes/website/blob/main/content/en/docs/tasks/extend-kubernetes/custom-resources/custom-resource-definitions
 .md)).

 That does not establish that an ordinary Longhorn chart bump will delete CRDs or underlying replica data. It establishes that a chart
 revision which removes or renames an unprotected CRD exposes a serious prune path.

 The parent also owns storage-related resources:

 ```console
   Application      longhorn-helm
   RecurringJob     backup-critical
   RecurringJob     backup-important
   RecurringJob     backup-standard
   StorageClass     longhorn-critical
   StorageClass     longhorn-important
   StorageClass     longhorn-standard
 ```

 Therefore “the child is where prune risk is real” is too exclusive. Both layers own consequential resources, though the child’s CRD
 ownership presents the sharper control-plane risk.

 No Entire checkpoint history is available:


 Git history nevertheless exposes the recorded commit intent. Commit b8d7e59 said:

 │ “Set prune: false on Longhorn app to prevent accidental PVC deletion”

 But its diff changed only the parent in apps/root.yaml:

 ```diff
    syncPolicy:
      automated:
   -    prune: true
   +    prune: false
        selfHeal: true
 ```

 apps/longhorn/application.yaml was not changed; its child prune: true dates back to the original 4448861 commit. The later AGENTS.md
 directive and architecture table inherited the parent-only state without documenting why the chart-owning child remained different.

 This history supplies no evidence that the split was deliberate. It instead points toward an incomplete safety control or an
 imprecisely scoped directive.

 Verdict

 Materially sound finding, overstated conclusion. The child really has automated pruning, owns 23 unprotected Longhorn CRDs, and is
 omitted from the documented exception despite the stated data-deletion rationale. That is a genuine policy and safety inconsistency.
 It is not yet a proven directive violation because AGENTS.md literally names the parent Application longhorn, while the child is
 longhorn-helm; nor is there evidence of a deliberate exception. The defensible finding is an undocumented, historically unexplained
 parent/child policy gap with a real conditional prune risk, not a conclusively intentional distinction or conclusively established
 violation.
