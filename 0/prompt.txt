Accepted — with source links, wave timing, and the proxy's `request completed` being header-time rather than stream-completion, that's settled.

Your remaining question is the one I have data for. Phoenix has token counts and wall-clock latency on every span from today's eleven manual runs — which the cluster logs don't carry.Wrong filter syntax — using the node IDs I already have.Eleven runs, and the throughput is the answer:

| Run      | Latency | Completion tokens | ms/token |
| -------- | ------- | ----------------- | -------- |
| P1       | 105,503 | 7,824             | 13.49    |
| P5       | 104,156 | 7,543             | 13.81    |
| P3       | 112,237 | 8,610             | 13.04    |

| Baseline | 124,590 | 9,134             | 13.64    |
| P2       | 128,966 | 9,319             | 13.84    |
| C2       | 122,193 | 8,819             | 13.86    |
| C3       | 127,852 | 9,729             | 13.14    |
| C5       | 139,253 | 10,032            | 13.88    |
| C4       | 143,337 | 10,681            | 13.42    |
| C1       | 144,186 | 10,491            | 13.74    |

**Generation rate is stable: 13.04–13.88 ms/token, a 6.5% spread across eleven runs at different times of day.** Type: OBSERVED.

So nothing is anomalous about particular streams. They don't vary — **the output length does.** That rules out slower generation and upstream queueing variance from your remaining-causes list; the throughput would have to wobble to support either, and it doesn't.

**The deadline is therefore a token budget.** At \~13.6 ms/token, 120,000ms buys roughly **8,800 completion tokens** (8,645 at the slowest observed rate, 9,205 at the fastest). Type: INFERENCE — it assumes span `latencyMs` covers substantially the same interval Phoenix's task deadline wraps. Refuted by any completed run above \~9,200 completion tokens.**And here's the part that stings.**

|                   | Mean completion tokens | vs \~8,800 budget           |
| ----------------- | ---------------------- | --------------------------- |
| Pre-contract runs | **8,448**              | under — most would have fit |
| Contract runs     | **9,950**              | over by \~13%               |

The DELIVERABLE contract added roughly **1,500 completion tokens per run**. Before it, mean output sat just under the deadline and 3 of 5 runs would have completed. After it, only C2 (8,819) is even borderline.

**The change that made the analysis rigorous is precisely what put it over Phoenix's wall.** Refutation coverage 1/6 → 5/5, self-assigned VERIFIED to zero, evidence table on every run — and about 1,500 tokens for it. The deadline doesn't care that the extra tokens were the good ones.

So your open question resolves without needing an upstream cause: the streams exceed 120 seconds because the prompt asks for \~9,950 tokens of output and the deadline funds \~8,800.

**Which quantifies the options rather than just listing them:**

- **Cut \~1,150 tokens of required output** (\~12% shorter). The evidence table is the cheapest target — 12–13 rows at present, and the rubric says load-bearing claims only. Ten rows would likely do it. Costs some coverage, keeps the model and the mechanism.
- **Faster model** — sonnet or haiku through the same proxy. Buys headroom at the price of comparability with everything already on the board.
- **Route around the deadline via SDK** — still a hypothesis, still unverified, still the only option that degrades nothing.

**One caveat I want on the record:** capping `maxTokens` to \~8,000 would be the wrong fix. It doesn't make the model concise, it truncates it mid-generation — and since the evidence table is the *last* section, you'd lose exactly the artifact we spent the day building. If you go the shortening route, it has to be the contract asking for less, not the ceiling cutting it off.
