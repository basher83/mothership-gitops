1. Write the pins directly instead of merging a pin PR. I agree with this. One
 adjustment: re-read the live versions right before committing. Auto-sync re-resolves a
 range whenever a new chart is published, so 8.41.1, 3.7.178 and 1.104.4 could move before
 the commit lands. Pin to whatever is live at that moment and the cluster doesn't change.

 2. Exclude argo-cd from automerge. This is the important one. Today 10.* gets no patch
 PRs, so the existing patch automerge rule never touches argo-cd. Once it's pinned to
 10.14.0, the next 10.14.x patch will automerge into Git and never deploy, because the
 gate is manual. That's the same "Git moved, cluster didn't" drift, now on a schedule. Add
 argo-cd to the substrate no-automerge rule, the one that already exempts longhorn and
 external-secrets.

 3. Prevent new ranges instead of auto-pinning them. The automerge-pin rule (option 2)
 works: mothership-gitops automerges today, and Renovate merged the Phoenix patches
 itself, gated by fast-gate → mise run ci → validate:gitops. After the pins are written by
 hand, though, it only matters if someone adds a range later. It's simpler to make
 validate:gitops fail on a range instead of skipping it, which also closes the gap the
 agent reported where validate:gitops skips ranged charts. Keep rangeStrategy: "pin" as a
 backstop, and skip the automerge-pin rule. - Automerge minors for homarr, netdata and tailscale-operator. Today these three take
   minor upgrades with no review at all. Automerge keeps that hands-off, and adds a
   commit, a PR and a render check to every upgrade. I'd include tailscale-operator:
   keeping it on manual review would add work compared with today.
 - Give them their own group, or none. A grouped PR only automerges if every update in it
   is marked automerge (config.automerge = upgrades.every(...) in Renovate's branch code).
   If they stay in ArgoCD Charts (Minor), minors for ESO, longhorn and radar (2.14.0,
   1.13.0 and 1.20.0 are pending right now) would block every automerge.
 - Consider minimumReleaseAge (e.g. 3 days, like the mise preset). It gives a buffer
   against a bad release on day zero. First confirm with a dry run that each chart repo
   publishes release timestamps. Renovate 4x holds updates that have no timestamp, and I
   haven't checked the tailscale chart repo. Suggested shape: one commit containing the exact pins, the rangeStrategy: "pin" rule,
 argo-cd added to the no-automerge rule, the minor-automerge rule for the three charts in
 a separate group, and the architecture.md rewrite. Then a separate commit that makes
 validate:gitops fail on ranges, and the #94 comment. Pushing them together with d531a3f
 and 1e77fb4 is fine.
